# C1 完整理解项目

## 本阶段目的

在与用户讨论方向前，先建立双方共享的事实基础。最低可用产物不是一份漂亮摘要，而是一份能让后续判断随时回到原文的项目工作记忆与来源索引。

## 输入

- 用户项目目录中的 Brief、招标书、会议纪要、研究、预算、产品资料、表格、历史方案和已有分析；
- 用户在当前对话中给出的目标与限制。

## 先做什么

1. 用文件检索列出全部候选资料，识别格式、大小、版本和重复文件。
2. 先完整阅读 Brief、会议决定和材料目录，再按决策相关性阅读其余资料。
3. 对大型文档分段读取，但必须覆盖全文；不得因为前几页已经形成印象就停止。
4. 区分：
   - 客户明确事实与要求；
   - 原始研究和数据；
   - 他人分析判断；
   - 历史方案答案；
   - 模型当前推论；
   - 仍待确认的未知。
5. 对相互矛盾的材料保留双方原意，不擅自选边。

“按决策相关性阅读”不等于只读汇总报告。进入 C2 前，至少完成以下覆盖：

- Brief、招标要求、会议决定等第一方边界；
- 会改变问题定义、方向选择或承诺的主要分析报告；
- 主要结论能够回查的原始数据、表格、图片或正文位置；
- 用户明确指定的参考方案；
- 无法读取或暂未读取的文件及其原因。

原始数据量过大时，不要求全文塞进上下文；先看字段、范围和代表性切片，再为后续回查记录定位。遇到表格、PDF 或图片不能因为当前文本工具打不开就宣告完成，应使用对应文件能力，或如实记录未覆盖及影响。

## 写入 `.proposal-work/source-index.json`

先保留全部发现文件的覆盖状态，再为会影响后续判断的资料记录语义作用。每个文件或明确的文件组至少记录：

- 相对路径；
- 资料类型和大致范围；
- `read_mode`：`full`（全文/全表覆盖）、`sampled`（大型原始数据按字段与代表切片读取）、`duplicate_or_derived`（重复、临时或已有更可靠上游版本）、`unread`（未读或失败）；
- 已实际读取的范围；若为抽样，记录字段、Sheet、页码或切片；
- 未全文读取或排除的原因及其对判断的影响；
- 它回答了哪些项目问题；
- 关键章节、页码、Sheet 或定位信息；
- 是否与其他材料冲突；
- 后续哪些判断应回到这里。

目录聚合项不能代替其中每个文件的覆盖状态。索引的目的是证明覆盖并快速回查，不要复制整份原文，也不要用“全部报告已读”代替逐项状态。

## 写入 `.proposal-work/project-memory.md`

只保留当前仍有效的项目理解：

1. 客户在采购什么，以及最终需要接受什么决定；
2. 必须交付什么；
3. 受众、品牌、产品、市场和竞争现实；
4. 预算、时间、渠道、资源与合规限制；
5. 资料已经证明的事实；
6. 当前关键张力与初步解释；
7. 高影响未知与冲突；
8. 明确不做什么；
9. 下一步最值得讨论的问题。

每条重要判断附简短来源定位。不要复制全部聊天，也不要把未证实推论写成事实。

同时写入“提案语言基线”，只保留会影响 C2 与 C3 的上游语言判断：

- 最终面对的听众，以及品牌、团队和项目应如何称呼；
- 整体更偏判断、启发、行动还是分析，判断强度如何；
- 允许使用的概念、比喻和情绪强度；
- 明确禁止的幕后称谓与高频 AI 句式；
- 3 条去项目化的正面示例。

这不是完整文案规范。它只保证方向讨论、Storyline 和页面架构从一开始就使用面向客户的提案语言；By-page P1 再根据参考方案细化。

## Wiki 第一次介入

项目工作记忆形成后，通过 Library 的 `scripts/query-wiki.mjs`限量查询少量相关 Lens：

- 只查询与当前关键张力直接相关的 Module/Lens；
- 用它寻找遗漏角度、挑战表面解释或改善问题定义；
- 不运行全库 Lens；
- 不用 Wiki 的历史答案覆盖项目事实；
- 至少形成一个完全从本项目材料出发的独立角度。

若具体查询返回 0 条：

1. 改查相关 Module、上位概念或更宽的关键词；
2. 仍为 0 条时，明确记录“本轮 Wiki 没有提供有效补充”；
3. 继续以项目材料形成判断，不把一次空查询算作已经使用 Wiki。

## 阅读完成回执与第一次互动

进入 C2 前必须先在对话中给出一次简洁、可核对的阅读回执：

1. 共发现多少文件或数据资产；
2. 全文覆盖、抽样读取、重复/衍生、未读/失败各多少；
3. 每份逻辑资料或合理文件组的一句话内容与用途；
4. 明确列出未全文读取、无法读取和排除项，以及是否影响方向判断。

文件数量、类型、大小、重复与读取范围是机械状态，优先由文件检索或脚本统计；模型负责解释内容和项目作用。原始数据很大时允许按合理文件组汇报，不在聊天中展开几百行清单，但不能隐藏未覆盖项。

用简洁语言呈现：

1. 阅读回执；
2. 我理解这个项目真正要解决什么；
3. 已确认的关键事实；
4. 最值得注意的矛盾或机会；
5. 我的初步判断；
6. 最多 1–3 个会显著改变方向的问题。

不要问资料已经回答的问题。若资料已经足够，可以直接提出方向假设，不为了互动而强行提问。

## 诚实终态

- 资料缺失：列出缺失内容会影响什么，并继续做不依赖它的理解。
- 文件无法读取：记录具体文件和失败原因，不假装已经看过。
- 资料冲突：保留冲突，交给后续判断或人确认。
- 资料很多：允许分批读取，但进入 C2 前必须完成覆盖。

## 完成标准

- `source-index.json`能够把关键判断定位回原资料；
- 阅读回执与 `source-index.json`一致，未用笼统完成声明掩盖抽样、排除或失败；
- `project-memory.md`足以让另一次模型运行恢复项目全景；
- 上游提案语言基线已经建立，C2/C3 不会先用分析报告或幕后语言形成结构；
- 已区分事实、分析、推论与未知；
- 所有决策相关材料均已覆盖，或已如实记录未覆盖项、原因与影响；
- Wiki 已产生实际补充，或已明确记录零结果和降级处理；
- 已带着理解和初步判断与用户开始对话。
