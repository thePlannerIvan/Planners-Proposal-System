# C3 Storyline 与页面架构

## 本阶段目的

把已经锁定的主方向组织成客户愿意接受的认知推进，并根据每个判断的证明负担展开为实际页面。Storyline 与 Page Architecture 在本阶段一次形成，不设置两个重复的人审门禁。

## 进入前检查

先读取 `project-memory.md`。只有以下内容已经明确，才能开始：

- 主方向；
- 选择理由；
- 它会改变哪些策略或行动；
- 最大风险或证据边界；
- 明确放弃项；
- 用户对深化后方向的确认。
- C2 中模型提出的关键问题、用户的真实回答，以及回答如何改变方向。
- 消费者、竞品、Brand Best Self 三圈的项目证据及其核心交集。

若方向仍是开放问题、只是用户最初提出的一句话、没有真实问答证据、没有可信三圈交集，或工作记忆仍保留已经失效的方向选择问题，回到 C2。这个检查是模型对工作记忆的语义确认，不新增 Contract。

## 先建立 Storyline

从客户最终需要接受的决定反向推导：

1. 接受这个决定必须先相信哪些关键判断；
2. 相信这些判断前必须理解哪些事实和矛盾；
3. 哪些认知是后续认知的前提；
4. 判断之间是因果、递进、转折、比较还是选择关系；
5. 哪些内容虽然有趣，却不影响最终决定。

Storyline 节点表示一次必要的认知变化，不是页面标题。可以使用建立共同事实、暴露矛盾、重定义问题、证明机会、提出方向、解释机制、转化行动和建立信心等认知动作，但不能把它们当固定目录。

## 回到资料

每个关键认知节点都要：

- 通过项目工作记忆定位相关原文；
- 检查事实是否真的支持该判断；
- 寻找相反材料；
- 控制结论强度；
- 记录后续展开应回查的来源。

此时不建立 Evidence Ledger。数字和事实的逐项精确核对在 By-page 实际使用后进行。

## Storyline 完成后，Wiki 必须再次介入

先完成一版完全由项目事实和主方向推导的 Storyline，并逐节点回到资料检查。**Storyline 尚未完成时不做本轮查询；Storyline 完成后、Page Architecture 开始前必须停下来查询 Wiki。** 不得先生成页面架构，再等用户指出缺少某个板块才补查。

围绕 Storyline 的每个主要认知板块，通过 Library 的 `scripts/query-wiki.mjs`限量查询相关 Module、Lens 或 Recipe。相邻节点可以共用一次有效查询，但消费者、竞品、品牌机会、内容/渠道机制、执行节奏与衡量等实际存在的主要板块都必须被覆盖。

本轮 Wiki 用于：

- 寻找合适的论述模式；
- 检查是否缺少必要证明环节；
- 学习复杂关系怎样展开；
- 参考从洞察进入策略与执行的成熟顺序；
- 参考可复用的页面论证结构。

对每个主要板块，明确比较：

- 当前 Storyline 已经包含什么；
- Wiki 提醒了哪些分析维度、证明顺序、内容块或页面角色；
- 哪些内容需要补入、拆开、合并或调整顺序；
- 哪些 Wiki 方法与本项目不相关，因此不采用。

将结果以简短自然语言写回 `project-memory.md`的“Storyline 后 Wiki 补全”部分，至少记录板块、采用的 Lens/Recipe ID 和实际改变；没有有效结果时记录查询词与零结果。它是防止 Wiki 被形式化跳过的工作记忆，不是新增 Contract。

Wiki 只能帮助“这个板块怎样完整讲清楚”，不能替项目决定“应该讲什么”，也不能引入项目材料中不存在的事实。

具体查询返回 0 条时，改查相关 Module、Recipe 上位概念或更宽关键词；仍无结果则明确记为“本轮无有效 Wiki 补充”，不要把空查询当成完成。

只有完成这次逐板块补全，才能开始把 Storyline 展开为 Page Architecture。

## 从 Storyline 展开为 Page Architecture

Storyline 节点表示认知变化，页面承担具体证明，两者不是一一对应。不要写完十几个 Storyline 句子后直接把它们改成十几页标题。模型在同一次工作中依次完成下面四遍思考，不新增文件，也不增加人工门禁。

### 第一遍：建立认知节点

先只判断客户的认知需要怎样推进。每个节点写清：

- 客户在这里原本怎样理解；
- 这一段要让客户新增或改变什么判断；
- 它为什么是下一步决策的前提。

### 第二遍：拆出证明负担

对每个节点追问“客户凭什么相信”。列出真正必须被看见的证明材料，例如：

- 事实与数据；
- 对象之间的比较；
- 原因、机制与解释；
- 产品、竞品、人群或案例的完整拆解；
- 对策略和行动的含义；
- 执行机制、资源、节奏与衡量。

此时不要先限定页数。如果一句 Storyline 需要五种不同证明，就先承认它有五项证明负担。

### 第三遍：组成独立证明单元

把证明材料组合成可以在一页内被清楚理解的独立单元。每个单元必须有一个主要判断，也要有足以让判断成立的完整内容块。以下情况通常意味着应展开为多页：

- 同时需要事实、比较与策略含义；
- 多个竞品、产品、人群或阶段各自需要完整拆解；
- 数据关系与解释机制无法在同一页形成清楚层级；
- 执行主张需要分别说明机制、资源、节奏和衡量；
- 一个标题下出现两个可以独立成立的主要判断。

例如，“竞品揭示了什么机会”可以是一个 Storyline 节点，但可能需要分别用页面完成：竞争格局、代表竞品的产品与定位、内容策略与达人矩阵、数据表现，以及由此导出的机会。不要因为 Storyline 只有一句话，就把这些压进一页。

反过来，若几个材料共同证明同一个判断、共享同一阅读层级，也不应为了增加页数机械拆散。

### 第四遍：做页面容量与冗余审计

在写入 JSON 前逐页检查：

- 这一页是否偷偷承担了两个独立判断或两次认知跳跃；
- 是否需要两套不同的大型表格、图表或视觉关系回答不同问题；
- 客户能否在一页中看清“判断—小论点—材料”的单一层级；
- 拆页后每页是否仍有独立证明任务，而不是把一句话切碎；
- 相邻页是否重复同一材料，只换了措辞；
- 页面总量是否足以承载 Brief，而不是追求看起来精简。

发现过载就拆页，发现重复就合并。页数服从论证完整性与一页可读容量，不服从 Storyline 节点数量，也不追求固定字数。

每一页最终必须有：

1. 一个主要判断；
2. 观点式标题意图；
3. 为证明判断所需的一个或多个完整内容块；
4. 后续取材需要；
5. 与前后页的自然关系。

内容块不是短句配额。它可以要求：

- 完整解释段落；
- 数据表格和结论；
- 趋势或比较图；
- 产品或竞品拆解；
- 图片与观察；
- 矩阵、模型或框架；
- 路线图、时间线或行动计划；
- 案例和机制；
- 其他最适合证明判断的形式。

例如一页竞品判断可以同时要求产品、核心定位、卖点和结论；下一页可以继续分析同一竞品的内容策略、达人矩阵和数据表现。内容多不等于文字堆积，关键是材料丰富、关系清楚并共同证明一个判断。

## Coverage

展开后检查：

- Brief 的必须交付是否都有落点；
- 每页是否服务说服链；
- 是否存在重复、填充、越界或应放附录的内容；
- 是否有主张比材料更强；
- 是否把后续图表和版式工作过早塞进 Co-creation。

只有结构确实依赖特定比较、顺序或数据关系时才填写 `chart_brief`或`layout_direction`，通常保持 `null`。

## 产物

按照 `contracts/page-architecture.md`写入：

```text
.proposal-work/page-architecture.json
```

运行 Validator。不要单独生成需要用户再次批准的 `storyline.md`。

Page Architecture 是给 By-page 取材和写作的语义骨架，不是提前写好的文章：

- `claim`用一两句清楚说明本页要证明的判断；
- `content_requirement`说明需要展示什么、为什么能证明，不预写连篇正文；
- 不把同一套抽象概念复制到每页；
- 如果一个字段已经开始包含完整论说段落，先拆清页面或内容块，而不是继续扩写 JSON；
- 品牌称谓面向客户，不使用“甲方、乙方”等幕后语言。

## 语言

继承 `project-memory.md`中的“提案语言基线”。Storyline 的措辞会决定后续整案的认知和语气，不能等到 By-page 才第一次定义语言。使用面向客户的清晰中文，避免连续使用：

- “不是 A，而是 B”；
- “不只 A，更是 B”；
- “真正的 X 是 Y”；
- 抽象名词堆叠；
- 看似锋利但没有事实支撑的反转句。
- “甲方、乙方、客户方要求”等幕后称谓。

结构阶段重点是判断准确和推进自然，不追求每页都成为金句，也不把同一个创意概念重复包装成每一页的答案。

## 完成标准

- Storyline 能说明客户认知如何改变；
- Storyline 完成后、页面展开前，Wiki 已覆盖每个主要板块，并记录采用的方法及其实际结构增量或零结果；
- 每个节点已经依次完成证明负担、独立证明单元和页面容量审计；
- 一个节点可按需要展开为多页，页数不再机械等于 Storyline 节点数；
- Page Architecture 保持简洁、可取材，没有预写成分析文章；
- 每页一个判断且内容构成完整；
- Coverage 没有明显缺口、重复或范围膨胀；
- Wiki 与资料的角色没有混淆；
- `page-architecture.json`通过验证；
- 可以直接进入一次完整结构审阅。
