# B3b：逐语义单元抽取、去项目化 Lens

## 本阶段在全流程中的作用

B3b 把每个语义单元中的可复用方法抽出来，并在同一步写好未来方案的页面论证结构。B2 负责“切小”，B3a 提供整套推导上下文；B3b 才判断每个单元是否真的含 Lens。

## 先证据，后抽象

对每个语义单元按顺序工作：

1. 记录原始观察、来源页和单元在 Recipe 中的角色。
2. 判断它是可重复执行的方法、只对本项目成立的案例结论、证据不足，还是没有 Lens。
3. 若有方法，写成一个明确问题、所需输入、4–7 个具体且不可互换的操作、输出类型、适用条件、跳过条件、失败模式和边界。
4. 选择主 Module；现有 Module 都不合适时使用 `new_module_candidate`，不要硬塞。
5. 同时设计页面结构，让未来写方案时知道怎样把分析结果组织成有说服力的页面。

## 去项目化是硬门槛

从 Lens 方法正文中清除：

- 品牌、品类、产品、人名、竞品名称；
- 具体 slogan、活动名、创意概念、场景填充值；
- 特定渠道、预算、数值、排期；
- 本项目的结论、机会点和策略主张。

不能简单删词。应把具体内容替换成方法需要的变量、输入类型、判断关系或输出槽位，同时保留真正可执行的推导逻辑。

每个候选 Lens 必须再经过两道反空壳检查：

1. **替换测试**：把名称换成另一个常见方法后，如果问题、操作和输出仍然基本成立，说明写得过泛。
2. **信息损失测试**：如果整条方法可以无损压缩成“分析资料—形成洞察—输出策略”，说明没有抽出原方案独有的论证动作。

出现以下任一情况时，不得为了数量硬写 Lens：

- 去项目化后少于 4 个可执行、不可互换的操作；
- 操作只是“收集、分析、总结、输出”一类通用动词；
- 看不出每一步使用什么输入、作什么判断、怎样推进到下一步；
- 页面结构只能复述操作名称，无法形成独立论证。

此时应使用 `case_only`、`insufficient_evidence` 或 `no_lens`，并在理由中说明被剔除的是项目结论、案例表达还是证据不足。

## 页面结构必须回答什么

每一页都写：

- 该页在论证中的目的；
- 它回答的问题；
- 需要哪些证据；
- 信息之间是并列、顺序、层级、比较还是因果；
- 从上一页承接什么、向下一页推进什么；
- 最常见的误用。

页面结构不是把 operations 一步一页，也不是固定图表模板。它描述“论证与表达角色”，允许未来根据材料增减页面，但至少形成两页有推进关系的结构。

完成页面结构后，逐项反查全部 `operations_zh` 和 `output_structure_zh`：

- 每个关键操作必须在至少一页中找到实际承载位置；
- 每个输出必须有页面负责形成、解释或收束；
- 多个操作可以由同一页共同承担，但不能因为满足“至少两页”就把后半段方法藏在 operations 里；
- 在 `page_structure_check` 中确认未覆盖操作和输出均为空，并用一句话说明覆盖逻辑。发现未覆盖项时先补页面结构，不能虚假填空。

## 允许终态

`lens_candidate`、`new_module_candidate`、`case_only`、`insufficient_evidence`、`no_lens` 都是正式结果。零 Lens 比空壳 Lens 更好。每个语义单元都必须有记录，不能只提交“看起来有价值”的少数单元。

## 输出和命令

任务包必须同时包含该单元原文、B3a Recipe 上下文、本文件全文和 `lens-extraction.schema.json`。模型必须逐个语义单元完成“观察 → 去项目化 → 反空壳检查 → Lens 或正式零结果”，不能只根据标题批量生成。输出 `lens-extraction/1.0.0` JSONL。

```bash
node scripts/validate-lens-extractions.mjs \
  --input <运行目录>/B3b/lens-extractions.jsonl \
  --units <运行目录>/B2/materialized/semantic-units.jsonl
```

Validator 会确保每个保留语义单元都有一条提取记录，并拒绝终态与 Lens 是否为空不一致、项目残留未清零、页面结构覆盖自检未完成和重复 ID；语义质量仍由模型在进入 B3c 前自检。
