# 内部工作流：逐页提案文案

## 目的与方法

本 Skill 不重新发散 Storyline。它把 Co-creation 已经确认的每页判断发展成可直接制作的完整页面内容：

```text
接收结构与项目记忆
→ 继承上游语言基线并细化页面语言
→ 为每页回到原资料准备材料包
→ 写少量代表性完整样页
→ 自动打开样页审阅
→ 按章完成全案
→ 只审计终稿实际使用的事实与数字
→ 自动打开完整文案审阅
→ deliverable/proposal.md + deliverable/assets/
```

模型的主要精力用于判断、取材和写作。脚本只负责来源定位、格式检查、审阅保存、图片管理和交付打包。

## 入口

项目目录必须存在：

- `.proposal-work/page-architecture.json`
- `.proposal-work/project-memory.md`
- `.proposal-work/source-index.json`
- `.proposal-work/reviews/structure/review-feedback.json`，且整体批准
- 原始项目资料

若结构没有通过审阅，读取 `../proposal-co-creation/WORKFLOW.md`并返回对应阶段。不要让用户重新解释 Brief。

## 项目目录

```text
<project>/
├── .proposal-work/
│   ├── page-architecture.json
│   ├── project-memory.md
│   ├── source-index.json
│   ├── copy-style-profile.md
│   ├── page-material-packs.json
│   ├── proposal-draft.md
│   ├── fact-audit.json
│   └── reviews/
│       ├── sample/
│       └── final/
└── deliverable/
    ├── proposal.md
    └── assets/
```

用户和下游最终只需要看到 `deliverable/`。不要把来源索引、审阅目录、材料包或事实审计散落在项目根目录。

不要额外创建没有下游消费者的 `conversation-log.md`、`work-log.md`、`execution-summary.md`或运行总结。写作状态已经由正式工作文件和审阅反馈保存。

## 运行方式

每次只读取当前阶段：

1. `stages/P1-handoff-and-style.md`：接收结构，继承并细化语言。
2. `stages/P2-page-material-packs.md`：按页回到资料准备材料。
3. `stages/P3-sample-calibration.md`：代表性完整样页与 HTML 校准。
4. `stages/P4-full-copy.md`：按章完成丰富、可制作的全案。
5. `stages/P5-fact-audit-and-review.md`：最终实际使用事实审计、完整审阅与交付。

Stage 是任务的唯一完整定义。不要把 `references/`一次性全部加载。

## 页面写作原则

每一页的核心是证明一个判断。一个判断可以有数个小论点，但每个小论点应展开成页面真正需要的内容，而不是几十字摘要。

页面内容可以是：

- 完整解释段落；
- 产品、竞品或案例的结构化拆解；
- 数据表格与结论；
- 图表及其真实数据关系；
- 图片与观察；
- 模型、矩阵和对比；
- 路线图、时间线和行动计划；
- 内容策略、达人矩阵、渠道分工或执行机制。

不是每页都必须很满，也没有统一字数配额。判断标准是：内容是否精准、丰富、完整，是否在一页容量内让客户理解并相信这个判断。

## 提案语言

默认使用提案现场的客户语气：

- 直接面向品牌、团队或业务说话；
- 先给判断，再给事实、解释和行动含义；
- 具体、克制、有选择，不写研究摘要或 AI 式口号；
- 不出现“甲方、乙方、客户方要求”等幕后制作语言；
- 避免连续使用“不是 A，而是 B”“不只 A，更是 B”“真正的 X 是 Y”；
- 不为显得锋利而制造没有事实基础的反转；
- 相邻页面主动变化句式和节奏。

语言由模型根据参考方案和 `references/proposal-language.md`判断，不运行机械语言 lint。

## 事实与数字

不预分类全部原始数据，也不建立全量 Evidence Ledger。只审计终稿准备实际展示或说出的：

- 数字与比例；
- 外部事实；
- 原话引用；
- 图表和表格数据；
- 计算结果；
- 会影响客户决定的关键断言。

单一审计入口从终稿标题与可见正文自动枚举数字事实，复用页面材料包和来源索引寻找来源，直接读取 Excel 全部工作表，归一化数值、单位与区间，并在文案修改后继承未变化事实的结果。缺失逐页材料包时立即返回 P2，不允许退化成全库数字碰撞。分析报告已经明确给出的汇总占比、均值、增幅或词频，以报告作为该汇总数字的直接来源，不要求回原始明细逐字匹配。每条事实中的数字分别归为来源事实、衍生事实、方案数字或非事实数字；脚本负责覆盖、读取、候选证据、数值定位、简单计算、机械确认和增量状态。模型只读取去重后的短队列，选择核实、带限定、修改文案或提交用户决定，再由脚本合并决定；不得凭记忆宣布已核对，不得直接修补机械状态，也不得通过改数字类型绕过错误。

## 审阅

- 样页和终稿都用 HTML，不把数页长文塞进聊天。
- 审阅页面必须自动打开，不询问“要不要启动”。
- 普通页面默认通过；含机器无法最终核实的事实例外时，该页必须由用户明确决定。
- 用户输入反馈时自动切换为“需要修改”。
- 页面主要展示标题、完整主体、表格、图表说明和图片。
- 页面任务、来源定位、转场和制作备注折叠。
- 终稿允许拖拽上传 PNG、JPEG、WEBP 或 GIF。
- 保存后让用户回到 Codex 发送“已完成”；不使用 WebSocket，不长期等待。

## 完成标准

- 没有无声改写已批准的 Storyline 与页面判断；
- 每页围绕一个判断，内容足以证明而不是摘要；
- 图表、数据表、图片和执行内容能被下游理解与制作；
- 实际使用事实已回到来源并完成语义核对；
- 提案语言面向客户且符合项目风格；
- 样页和终稿审阅均由脚本自动打开；
- 最终反馈与当前文案 Hash 一致并整体批准；
- 交付只包含 `deliverable/proposal.md`和相关图片。

## 运行后迭代

项目特定语言偏好写入 `.proposal-work/copy-style-profile.md`。单次改句不升级 Skill；连续出现的取材、事实审计、页面厚度或审阅问题只记录为系统维护问题。生产运行不读取未发布的 `_internal/`；失效模板、旧 Ledger 与无调用脚本移出 Active 路径。
